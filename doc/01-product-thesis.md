# Product Thesis

## Problem

Software projects accumulate hundreds of tasks that are real but
economically awkward:

- small bug fixes;
- tests;
- documentation;
- dependency updates;
- UI polish;
- issue reproduction;
- research;
- small integrations;
- refactors;
- migration work.

A full-time developer may not want to interrupt a larger task for them.
A freelancer may not want a tiny contract. The project owner therefore
keeps the backlog.

At the same time, a growing group of developers has access to
increasingly capable coding agents and has spare capacity outside their
primary projects.

## Proposed solution

Create a structured exchange where work can be decomposed into
**bounded, verifiable task capsules**.

A task capsule contains:

- objective;
- scope;
- relevant files;
- acceptance criteria;
- test commands;
- security constraints;
- reward;
- deadline;
- required skills.

The contributor does not need to understand the entire project.

## Positioning

Weak positioning:

> “Upwork but with Claude Code.”

Stronger positioning:

> “Turn your software backlog into work other developers can safely pick
> up.”

Contributor-side positioning:

> “Turn spare developer + AI capacity into useful credits.”

## Product principles

### 1. Human-controlled

AI can assist, but the platform does not silently operate someone’s
subscription or computer.

### 2. Bounded

Small tasks are preferable to ambiguous projects.

### 3. Verifiable

Every task should have measurable acceptance criteria whenever possible.

### 4. Reputation-backed

A contributor’s history matters more than a generic star rating.

### 5. Credit-native

Credits should unlock useful ecosystem value, not merely imitate cash.

### 6. Open by default

The first environment should favor open-source and low-sensitivity
repositories.

## Product moat hypothesis

The long-term moat is unlikely to be the task board itself. The
defensible asset could become a dataset of:

- task difficulty;
- actual completion time;
- acceptance rates;
- contributor expertise;
- task failure patterns;
- AI-assisted productivity;
- review effort;
- security incidents;
- credit pricing.

That data could improve task pricing, matching, risk scoring, and task
decomposition.

## Non-goals for v1

- remote computer control;
- sharing paid AI accounts;
- production access;
- autonomous deployment;
- anonymous high-value work;
- cash withdrawal;
- unrestricted private repository access.

## Success definition

The product succeeds initially if a contributor can repeatedly answer:

> “I have 30 minutes and my coding agent. What useful thing can I
> complete right now?”

and a builder can repeatedly answer:

> “I have a small task I don’t want to do. Can I safely delegate it?”
